## UNO 全屏下识别转屏（v22）
- 用户反馈全屏后识别不到转屏。根因：进入全屏时浏览器锁定当前方向，`orientationchange`/`resize` 不触发，轮询读到的 `screen.orientation.angle` 也冻结。
- 增加三道保险：①监听 `fullscreenchange`/`webkitfullscreenchange`，进入全屏时调用 `screen.orientation.unlock()` 解除方向锁定并立即重检方向；②监听 `screen.orientation` 的 `change` 事件主动更新；③保留 250ms 轮询兜底。
- `tryFullscreen` 增加已在全屏判断（`fullscreenElement` 存在则直接 return），避免全屏下 repeat requestFullscreen 报错/闪烁。
- 缓存版本升至 moyu-v22，已部署并通过 curl 200 验证。注意：极少数手机厂商 ROM 仍会强制锁死全屏方向，属浏览器/系统限制，无法完全突破。

## UNO 修复"进入游戏后转屏识别不了"（v23）
- 根因：v17 恢复的"开局自动全屏"（`startMatch` 内 `this.tryFullscreen()`）在用户点"开始游戏"瞬间进入全屏，浏览器锁定当前方向，之后物理转屏页面不跟随 → "进入 UNO 后转向识别不了"。构造函数的 `armedFullscreen`（首次触摸触发全屏）也加剧此问题。
- 修复：删除 `startMatch` 的自动 `tryFullscreen()` 调用；删除构造函数的 `armedFullscreen`/`fsHandler` 及 `pointerdown` 监听；删除 `updateOrientation`/`pollOrientation` 里的 `armedFullscreen=true`。游戏默认在窗口模式运行，转屏由 resize/orientationchange/matchMedia/250ms 轮询多重保障可靠识别。
- `tryFullscreen` 改为可切换：已在全屏时点击 ⛶ 退出全屏（退出后即可正常转屏）；⛶ 按钮保留为手动全屏入口。
- 教训：全屏 API 与转屏检测在手机上本质冲突；要"识别转屏"就不能"自动全屏"，只能让用户手动触发全屏。
- 缓存版本升至 moyu-v23，已部署并通过 curl 200 验证。

## UNO 方向环 1:1 移植桌面代码（v26）
- 用户质疑：为什么不直接用桌面项目 test/src/UnoGame.java 的 drawDirectionRing，而是自己复刻导致方向反了。
- 根因：手机端 v25 自己套了一套 y 向上极坐标 `(cy - r·sin)`，箭头切向公式符号搞反（本应是 (-sinA, cosA) 顺时针切向，却写成带负号导致逆时针），所以箭头"反向"。
- 修复：dirRingSVG 完全重写为桌面 drawDirectionRing（UnoGame.java:1613）的 1:1 移植——y 向下坐标系 `(cx + r·cosA, cy + r·sinA)`；ARC_SPAN=π·0.72≈130°；两条弧相隔 180°；每条弧两端各一个箭头（共 4 个）；箭头切向 = direction·(-sinA, cosA)，由 this.direction 控制朝向（1=顺时针/-1=逆时针）；basePhase 固定 -π/2，自转交给 CSS .cw/.ccw 动画。
- 注意：v26 恢复为桌面原始"4 个箭头"设计（v25 为迎合用户"两个圆弧"观感减到了 2 个箭头），但箭头做小、贴弧端，缺口明确，整体仍是"两条弧"观感。若用户仍嫌箭头多可再减。
- 部署接口首次连续 2 次 400（CloudStudio 瞬时抖动），第 3 次成功；curl 验证 HTTP 200。缓存版本升至 moyu-v26。
