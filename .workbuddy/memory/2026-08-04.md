将原 Java Swing 桌面客户端（登录/注册 + 摸鱼中心主页 + 4 个游戏）整体改写为手机可点可玩的 Web 单页应用。

## 修复 2048 对决模式"总是平局"的 Bug

### 问题根因
`Game2048DuelGame.handleGameOver()` 解析服务端返回的对决结果时，用 `resultsData.split(",")` 按逗号切分玩家，再 `split(":")` 取 4 段。但服务端实际格式（与 Minesweeper/Tetris 一致）是用 `;` 分隔玩家、每个玩家为 `name,result:time:score`。因此 2048 的切分方式让每条记录都因 `parts.length < 4` 被丢弃，`playerScores` 为空 → `winner` 恒为 null → 对话框永远显示"平局！"。

### 修复内容（Game2048DuelGame.java）
1. 解析改为 `resultsData.split(";")` → 每条 `split(",", 2)` 得 name 与 `result:time:score` → 再 `split(":")` 取 result/time/score（对齐服务端）。
2. 增加真正的平局判定：最高分若被多人并列（`bestCount > 1`），`winner` 置 null 显示"平局！"，而非默认把第一个玩家判为胜者。

### 编译
客户端 `javac -d /tmp/jc_out src/*.java` 通过（EXIT=0）。

## 飞行棋点击真正根因：devicePixelRatio 错位（moyu-v7）

### 结论：上一条"只是旧标签"判断不全面——还有真 bug
- 真正根因在 `onClick` 的坐标换算：`resizeBoard` 画布内尺寸用 `Math.min(window.devicePixelRatio||1, 2)`（dpr 上限压到 2），但 `onClick` 却用**原始 `window.devicePixelRatio`** 并拿 `boardCanvas.width/dpr` 算偏移。
- dpr≤2 时两者一致（旧桩用 dpr=1，所以"通过"掩盖了 bug）；**多数手机 dpr=3**（安卓/新 iPhone），此时 `boardCanvas.width/dpr = cssSize*2/3`，点击坐标被整体压缩、原点偏移算错 → 点到格子错位、大半落空 → "点了没反应"。

### 修复
- `onClick` 改为**全程 CSS 像素空间**计算：`mx=e.clientX-rect.left`，`ox=(rect.width-boardPx*boardScale)/2+PAD*boardScale`，不再引用 `window.devicePixelRatio` 与 `boardCanvas.width`。与 `drawBoard` 的视觉位置完全对应，所有 dpr 通用。
- 顺手修 `drawBoard` 清屏：原 `clearRect(0,0,cw,ch)` 在变换坐标系下只清到 `cssSize*dpr*boardScale`（< 全画布），可能留残影；改为先 `setTransform(1,0,0,1,0,0)` 再 `clearRect(0,0,boardCanvas.width,boardCanvas.height)` 清整块。

### 验证（关键，避免再"还是没反应"）
- 写纯几何脚本 `_test_ac_geom.js` 精确复刻新旧两套公式，在 dpr=1/2/3 × 4 基地 + 13 路径格：
  - NEW：dpr1/2/3 全部 0 失败 → PASS；
  - OLD：dpr=3 时 `4/4` 基地失败、`8/13` 路径失败 → 确认即用户所遇。
- `node -c` 通过；`rm _test_ac_geom.js`。
